# Описание тестовых кейсов:

Поскольку на бэк к нам прилетает JSON объект, должный содержать требуемые в рамках задачи поля, то при описании стоит выделить также такие кейсы валидации, 
когда требуемое поле отсутствует, при этом не стоит осуществлять отдельную проверку на пустоту входящего списка в целом, так как каждый кейс проверки поля на
отсутствие оного, целиком покрывает данную проверку. Так же в рамках обеспечения user experience, можно изменить проверку наличия пробела в поле на проверку,
где будем искать пробел в конкретном месте значения поля, ибо пользовать может случайно/по привычке нажать пробел до/после значения поля, и тем более на бэке
все равно будем делать проверки на пустоту по типу trim($field_name) !== ''. Далее, при указании длины поля в 0 символов, я буду исходить из предположения, что на бэке всегда будем делать операцию trim перед валидацией данных.

# Интеграционное тестирование

## front - back

В рамках тестирования front - back можно выделить несколько кейсов предполагаемого поведения - использование фронта as is, то есть мы предполагаем рутинный сценарий действий пользователя по заполнению/незаполнению форм и отправки данных на сервер: В рамках данного кейса не предполагается несколько групп ошибок - ошибки, связанные с неуказанием наименования поля перед упаковкой в JSON объект, то есть рутинно должны отправлятся все поля, если таковое не указано, значением по умолчанию предполагается пустая строка. Но возможен кейс нерутинного использования, когда пользователь может путем изменения кода фронта удалить определенное поле из списка или изменить его тип. Подобные ошибки были описаны в модульном тестировании как "Если 'поле' имеет отличный от строки тип/Если 'поле' не найдено в списке входящих параметров". Далее в кейсах интеграционного тестирования фронта я буду описывать кейсы как рутинного использования фронтенда, так и нерутинного.

На бэке в PaymentController используем моки для репозитория и сервиса оплаты A. Мок метода репозитория setOrderIsPaid возвращает true, мок метода сервиса оплаты A возвращает "{"process":true, "transcation_id": "transcation_id", "code"; 200}";

## back - repository

    Окружение - В рамках связки бэк - репозиторий предполагается наличие асинхронного воркера, который будет обрабатывать платежи, оплата за которые прошла, но потом возникла ошибка на бэке - далее рассматривается единственный кейс такой ошибки, а именно - ошибка бд при записи оплаченного заказа. Данный воркер должен будет передавать в платежный сервис A идентификатор платежной транзакции со статусом refund для перевода денег обратно клиенту. Конкретно в рамках данного кейса мы тестируем связку бэк - репозиторий, и соответственно, будем мокать данный воркер.

    В репозитории должны быть следующие методы: 

    checkPaidOrderIsExists(string $order_number): bool - должен проверять наличие в базе оплаченного заказа и который всегда должен вызыватся до вызова метода платежного сервиса A.

    checkSumIsValidForOrderNumber(string $order_number, float $sum): bool - должен проверять соответствие суммы заказа номеру заказа и который всегда должен вызыватся до вызова метода платежного сервиса A.

    setOrderIsPaid(string $order_number, float $sum): bool - должен осуществлять запись номера заказа успешно совершенного платежа и его суммы в базу данных.

    Метод репозитория мы вызваем из контроллера оплаты, в котором мокаем сервис оплаты A, с моком метода оплаты, должным возвращать "{"process":true, "transcation_id": "transcation_id", "code"; 200}" Репозиторий использует тестовую базу данных.
    
    На бэке в контроллере оплаты PaymentController используем мок для сервиса оплаты A, репозиторий используем реальный с тестовой базой данных.

    Таким образом: 

    PaymentController->содержит[PaymentService:Mocked, PaymentRepository:Real, PaymentWorker:Mocked]
    PaymentRepository->содержит[DatabaseConnection:Real]
    DatabaseConnection->осуществляет соединение с тестовой базой данных           
 

    1) В случае, если метод checkPaidOrderIsExists возвращает true для переданного номера заказа, то выбросить исключение PaidOrderAlreadyExists с последующим возвращением клиенту ответа с кодом 409.

    2) В случае, если в методе checkPaidOrderIsExists происходит ошибка соединения с базой данных/инконсистентности вводимых плейсхолдеров к кл-ву параметров и прочее, то выкинуть в репозитории исключение DatabaseException, которое перехватывается в бэке и выбрасывается в исключение ServerException с последующим возвращением клиенту ответа с кодом 500.

    3) В случае, если в методе checkSumIsValidForOrderNumber происходит ошибка соединения с базой данных/инконсистентности вводимых плейсхолдеров к кл-ву параметров и прочее, то выкинуть в репозитории исключение DatabaseException, которое перехватывается в бэке и выбрасывается в исключение ServerException с последующим возвращением клиенту ответа с кодом 500.

    4) В случае, если в методе checkSumIsValidForOrderNumber значение суммы платежа является равным или меньше нуля, вернуть на бэк false, бэк выбрасывает исключение BadDataException с последующим возвращением клиенту ответа с кодом 400.

    5) В случае, если в методе checkSumIsValidForOrderNumber значение суммы платежа несоответствует номеру заказа, то вернуть на бэк false, бэк выбрасывает исключение ConflictDataException с последующим возвращением клиенту ответа с кодом 409.

    6) В случае, если в методе checkSumIsValidForOrderNumber происходит ошибка соединения с базой данных/инконсистентности вводимых плейсхолдеров к кл-ву параметров и прочее, то выкинуть в репозитории исключение DatabaseException, которое перехватывается в бэке и выбрасывается в исключение ServerException с последующим возвращением клиенту ответа с кодом 500.

    7) В случае, если в методе setOrderIsPaid происходит ошибка соединения с базой данных/инконсистентности вводимых плейсхолдеров к кл-ву параметров и прочее,
    то выкинуть в репозитории исключение DatabaseException, которое перехватывается в бэке и выбрасывается в исключение ServerException с последующей передачей идентификатора платежной транзацкии, ранее возвращенной из мока, в мок воркера, с последующим возвращением клиенту ответа с кодом 500.

    8) В случае, если в методе setOrderIsPaid  выясняется, что оплаченный заказ существует в бд, то выбросить в репозитории исключение PaidOrderAlreadyExists, которое перехватывается в бэке и выбрасывается в исключение ServerException, далее осуществляется  передача идентификатора платежной транзакции моку воркеру. Клиенту возвращается ответ с кодом 520.



## back - payment_service
    Окружение - сервис оплаты А представляет sandbox сервиса оплаты.

    1) В случае, если сервис оплаты не отвечает, выбросить PaymentServiceIsNotAvailable, клиенту вернуть код 500.
    2) В случае, если сервис оплаты вернул ответ с кодом 200, выполнить setOrderIsPaid репозитория (рассматриваем успешный кейс - иные случае описаны в секции back - repository) и вернуть клиенту ответ с кодом 200.
    3) В случае, если сервис оплаты вернул ответ с кодом 403, вернуть клиенту ответ с кодом 403.



## back - worker
    Окружение - воркер представляет собой действительный воркер, инкапсулирующий мок сервиса A оплаты.

    1) В случае, если воркер не отвечает, выбросить исключение WorkerIsNotAvailable, клиенту вернуть код 520
    2) В случае успеха, воркер возвращает ответ ['accepted' => true] 



# Системное тестирование
Окружение - sandbox сервиса оплаты А и репозиторий с подключением к базе данных.

    1) Если один/несколько параметров из ['card_number', 'card_holder', 'card_expiration', 'cvv', 'order_number', 'sum'] отсутствуют/не являются корректными, то:
        Клиент -> backend -> валидация списка входящих параметров -> валидация списка входящих параметров |EXCEPTION| -> возврат сообщения об ошибке с кодом 400 -> клиент -> вывод сообщения об ошибке валидации.

    2) Если один/несколько параметров из ['card_number', 'card_holder', 'card_expiration', 'cvv'] не являются действительными, то:
        Клиент -> backend -> валидация списка входящих параметров -> проверка в репозитории номера платежа -> backend -> запрос к сервису оплаты A |403 response| -> backend -> возврат ошибки 403 -> клиент -> вывод сообщения об ошибке "Не удалось списать данные с карты, проверьте реквизиты"

    3) Если сумма платежа несоответствует номеру заказу, то:
        Клиент -> backend -> валидация списка входящих параметров -> проверка в репозитории номера заказа на предмет оплаты -> backend -> проверка в репозитории соответствия суммы платежа номеру заказа -> backend |EXCEPTION| -> возврат ошибки 409 с телом ответа "Сумма платежа несоответствует номеру заказа" -> клиент -> вывод сообщения об ошибке "Номер платежа несоответствует номеру заказа"
    
    4) Если оплаченный заказ существует в системе, то:
        Клиент -> backend -> валидация списка входящих параметров -> проверка в репозитории номера заказа на предмет оплаты -> backend |EXCEPTION| -> возврат ошибки 409 c телом ответа "Данный заказ уже существует в системе" -> клиент -> вывод сообщения об ошибке "Данный заказ уже существует в системе"

    5) Если сервис оплаты A недоступен, то:
        Клиент -> backend -> валидация списка входящих параметров -> проверка в репозитории номера заказа на предмет оплаты -> backend ->  проверка в репозитории соответствия суммы платежа номеру заказа -> backend -> запрос к сервису оплаты A |ERROR| -> backend -> возврат сообщения об ошибке с кодом 500 -> клиент -> вывод сообщения об ошибке "Сервис оплаты временно недоступен, повторите операцию позднее"

    6) Если возникли ошибки бд во время вызова checkPaidOrderIsExists репозитория, то:
        Клиент -> backend -> валидация списка входящих параметров -> проверка в репозитории номера заказа на предмет оплаты|ERROR| -> backend -> возврат сообщения об ошибке с кодом 500 -> клиент -> вывод сообщения об ошибке "Сервис временно недоступен, повторите операцию позднее"

    7) Если возникли ошибки бд во время вызова checkSumIsValidForOrderNumber репозитория, то:
        Клиент -> backend -> валидация списка входящих параметров -> проверка в репозитории номера заказа на предмет оплаты -> backend -> проверка в репозитории соответствия суммы платежа номеру заказа|ERROR| -> backend -> возврат сообщения об ошибке с кодом 500 -> клиент -> вывод сообщения об ошибке "Сервис временно недоступен, повторите операцию позднее".

    8) Если возникли ошибки бд во время вызова setOrderIsPaid, то:
